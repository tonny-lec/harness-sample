# 計画
フェーズ1成果物(AGENTS.md ルール・3 hook・worklog)を実機 codex で検証。検証項目は設計書の (a)〜(e)。

# 仮説と検証結果
- (a) 記録トリガー: ✅ タスク中の選択・判断の時点で working-notes.md が二部構成で作成された
- (b) PreCompact/PostCompact: ✅ /compact でスナップショット保存・通知・鮮度警告(touch で mtime を古くして確認)が動作
- (c) SessionStart 注入: ✅ 再起動後、ノートの状態を踏まえた応答が返った
- (d) 状態セクション上書き: ✅ 冒頭セクションは追記でなく上書きで最新化された
- (e) worklog 化: ⚠️ worklog エントリ作成と index 追記は行われたが、working-notes.md が削除されなかった
  - 再検証(2026-08-03、ルール修正 76318d9 後): ✅ Codex は既存 worklog がノートの内容を包含していることを確認したうえで、重複エントリを作らず working-notes.md の削除のみを実行した。迷いなく完了時ルールが優先された

# 発見
1. 初回検証時、Codex 側で superpowers 系スキルが発動して作業ディレクトリがスキル固有のディレクトリへ移動し、リポジトリ直下前提の規約パス(working-notes.md / docs/worklog/)が解決できず検証が中断した。回避策: スキルを無効化して再実施(成功)。cwd を移動させるスキルとの併用では本ハーネスのパス解決が壊れる。
2. (e) の原因は Codex 自身の説明によると「推論の記録は追記する」(平時ルール)と「完了時に worklog へ移す」(終了時ルール)の優先関係が不明瞭だったこと。

# 判断とその理由
AGENTS.md の完了時ルールに「working-notes.md を削除する。完了時はこの手順が『追記する』ルールより優先される」と明記して解消(このコミットで実施)。採らなかった案: hook による自動削除 — タスク完了の判定はモデルにしかできず、hook では決定論的に判定できないため。

# 判断の再検証
2026-08-03 に (e) を実機で再実行。修正後ルールのもとで Codex は「worklog は既存・成果物はコミット済み・残るは削除のみ」と状況を正しく判定し、重複 worklog を作らずノートだけを削除した。ルール文の優先関係の明記が有効だったことを確認。5項目すべて ✅ となりフェーズ1の検証は完了。

# 失敗から得た知識
- 規約パスは cwd に依存する。cwd を移動させるスキル(worktree 分離など)と併用する場合はパス解決の再設計が必要(フェーズ2以降の検討事項)。
- 行動ルールは平時と終了時の優先関係まで明示しないと、モデルは保守的に平時ルールへ倒す。
