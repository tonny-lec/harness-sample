# 設計: 知識抽出の成否中立化(「失敗から得た知識」の拡張)

日付: 2026-08-05
先行設計: [状態外部化の設計](2026-08-01-state-externalization-design.md)、
[worklog の記憶化の設計](2026-08-04-memory-bundle-design.md)、
[記録・検索ルールの発火保証の設計](2026-08-05-rule-firing-reinforcement-design.md)

## 背景と課題

記録の内容ガイド 5 項目のうち、明示的に「知識」と名指しされた受け皿は
「失敗から得た知識」だけである。その結果、次の非対称が生まれている。

- 失敗 → 「失敗から得た知識」として蒸留された教訓になる
- 成功 → 「仮説と検証結果」に結果として記録されるだけで、再利用可能な
  事実・知識の形に昇華する圧力が構造にない

「✅ だった」という結果と「X は Y という条件で成立する(確認済み)」という
確定事実は情報の質が異なる。検証で得られる知識は成否と無関係であり、
本質的な条件は「**不確実だったことが確定したか**」である。

一方、無条件に「成功も書く」とすると、自明な成功(テストが通った・コマンドが
動いた)がノイズとして蓄積する。失敗に偏った既存構造には「失敗 = 予想との
ズレ = 情報量が多い」という合理性があり、これを捨てずに拡張する必要がある。

## 決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| 項目名 | 「失敗から得た知識」→「**確定した事実と知識**」 | 成否ではなく確定性が本質であることを名前に出す。見出しとして短い |
| 記録条件 | 不確実だったことが検証で確定したら、成功・失敗を問わず書く。**自明な成功は書かない** | 「成功も全部記録」はノイズ。仮説の確認(成功)も棄却(失敗)も情報だが、最初から自明だった結果は情報ではない |
| 条件の置き場 | AGENTS.md の内容ガイドに括弧書きで織り込み、memory 書式ガイドの説明文にも 1 文追加 | ルール本文と書式ガイドの両方で読める。独立した箇条書きを増やしてルールを肥大させない |
| 既存記憶の扱い | 4 件(`readme-authoring` / `superpowers-usage` / `proofreading` / `post-compact-review`)の見出し `# 失敗から得た知識` を**一括で改名**。内容は不変、`generated.at` も更新しない | 記憶は更新統合型の「生きた文書」であり、現行書式と揃える。見出し改名は知識自体の更新ではないため timestamp は動かさない |
| 過去文書の扱い | specs / plans / 文書内の過去の経緯記述は書き換えない | 歴史的記録の改変を避ける(従来方針の踏襲) |
| hooks / tests | 変更なし | リマインダー文言は見出し名に言及していない(確認済み)。ルールの語彙変更のみで機械層に影響しない |

## AGENTS.md の新文面

記録の箇条書き(行動境界アンカー)の内容ガイド部分を次のように改める
(変更は最終項目のみ。他の箇条書きは不変):

```markdown
- コマンド・テスト・検証を実行して結果を確認した直後、その時点の推論を
  担当タスクのノートに記録する。タスクの大小を問わない。記録するのは
  行動ログではなく推論: 計画 / 仮説と検証結果(予想と合っていたか)/
  発見 / 判断とその理由(採らなかった案を含む)/ 確定した事実と知識
  (不確実だったことが検証で確定したら、成功・失敗を問わず書く。
  自明な成功は書かない)。
```

## エッジケースの扱い

- **「発見」との使い分け**: 「発見」は検証を経ずに気づいた事実・観察
  (コードを読んで分かった構造、予想外の挙動の観察)、「確定した事実と知識」は
  仮説を立てて検証した結果として確定したこと。境界が曖昧な場合はどちらかに
  書けばよく、厳密な振り分けは要求しない(受け皿が存在することが目的であり、
  分類の正確性は目的ではない)。
- **自明性の判断**: 「自明な成功」かどうかはエージェントの判断に委ねる。
  判断基準の目安は「検証前に結果へ賭けろと言われたら迷ったか」。迷いがなければ
  自明であり書かない。
- **既存記憶の「失敗から得た知識」の内容**: 改名後もそのまま有効(失敗由来の
  知識は新項目の部分集合)。書き直しはしない。

3. `python3 tests/test_post_tool_use.py && python3 tests/test_pre_compact.py` が
   green のまま(hooks / tests 無変更の確認)。
4. 実機(移行後の運用で観察): 成功で終わった検証タスクの完了時に、確定した
   事実が記憶へ知識として書かれるか。
