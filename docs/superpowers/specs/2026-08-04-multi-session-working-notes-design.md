# 設計: working-notes の複数セッション対応

日付: 2026-08-04
先行設計: [状態外部化の設計](2026-08-01-state-externalization-design.md)(本書はその一部決定を改訂する)

## 背景と課題

先行設計は作業ノートをリポジトリ直下の単一ファイル `working-notes.md` に固定した。
実務では同じリポジトリ・同じディレクトリで複数セッションを並行起動し、それぞれ別の
タスクを進める。このとき次の問題が起きる。

- 各セッションが同じ `working-notes.md` に書くため、冒頭の「現在の状態と次の一手」
  (常に上書きする設計)を後発セッションが潰す。
- SessionStart hook はどのセッションのノートかを区別せず、最後に書かれた内容を
  全セッションへ注入する。
- PreCompact の鮮度警告(mtime 判定)は、他セッションの更新で誤って抑制される。

## 決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| ノートの単位 | タスクごとに `working-notes/<topic>.md`(git 管理外)。`<topic>` は完了時の worklog `YYYY-MM-DD-<topic>.md` と同じ短いケバブケースの語 | セッション ID ではなくタスク名を鍵にすることで、別セッション・別ハーネスから同じタスクを再開できる(先行設計のハーネス中立方針を維持)。完了時のアーカイブ単位とも一致する |
| ノートの発見 | エージェントがタスク開始時に `working-notes/` を確認し、担当タスクのノートがあれば読んで再開、なければ作成する。他タスクのノートは編集しない | hook はセッションとタスクの対応を知り得ないため、対応付けはエージェントの判断(AGENTS.md ルール)でしか行えない |
| SessionStart hook | **廃止**(hooks.json から削除、`session_start.py` とそのテストも削除) | 複数ノートの状態を全部注入するのはコンテキスト管理の放棄に等しく、「最新 1 件だけ注入」はこのセッションのタスクと一致する保証がなく誤誘導になる。発見・再読は instructions 層に常駐する AGENTS.md ルールへ一本化する |
| PreCompact の鮮度警告 | **廃止**。transcript スナップショット退避は変更なく維持 | hook はこのセッションがどのノートを使っているか知らない。ディレクトリ内の最新 mtime で判定すると他セッションの更新が警告を抑制し(偽陰性)、信頼できないシグナルになる。不正確な警告は無いほうがよい |
| PostCompact hook | 維持。通知文言を「担当タスクのノート(`working-notes/<topic>.md`)を読み直す」に改める | 機能は従来どおり通知のみ |
| ノート内部構造 | 変更なし(冒頭「現在の状態と次の一手」は上書き、以降「推論の記録」は追記) | 二部構成の理由(次の判断に必要な状態の維持)はノートが複数になっても変わらない |
| 完了時の処理 | 自分のノートだけを OKF 形式で `docs/worklog/YYYY-MM-DD-<topic>.md` へ移し、`index.md` に 1 行追記し、ノートファイルを削除する | 従来ルールをノート単位に読み替えるだけ。他セッションのノートを編集しないことを明文化する |
| git 管理 | `.gitignore` を `working-notes.md` / `working-notes/` / `.harness/` の 3 行構成にする(旧 `working-notes.md` は移行安全策として維持) | ディレクトリ化に追従しつつ、旧ファイルが残っている間の誤コミットを防ぐ(最終レビュー指摘 #1 反映) |
| 既存ノートの移行 | 自動化しない。README に「残っている `working-notes.md` は手動で `working-notes/<topic>.md` へ移す」と 1 行記す | 一度きりの操作に機構を作らない(YAGNI) |

## 先行設計からの改訂点の整理

先行設計 1-4 節「SessionStart hook」は、「再開時にノートを読む」をプロンプト規範では
なく設定で保証するために導入された。本設計はこの保証を手放し、AGENTS.md ルールに
戻すトレードオフを明示的に受け入れる。理由は上表のとおり: 複数ノート下では機械的
注入が「正しいノートを選べない」ため、保証したい内容(自タスクの状態の復元)を
そもそも hook では実現できない。

PreCompact の役割は「モデルを介さない決定論的退避」に純化される。鮮度警告の喪失は、
平時の随時記録ルール(主防御)が機能していれば影響が小さい。

## AGENTS.md の新ルール文面

```markdown
## 推論の外部化

- タスク開始時に `working-notes/` を確認する。担当タスクのノート
  `working-notes/<topic>.md` があればそれを読んで再開し、なければ作成する
  (`<topic>` は完了時の worklog と同じ短いケバブケース)。
  他タスクのノートは読んでよいが、編集しない。
- 次のいずれかが起きたら、その時点で担当タスクのノートに記録する。
  タスクの大小を問わない:
  - 複数の選択肢から選んだ 1 つとその理由(採らなかった案とそれぞれの理由を記載)
  - 仮説を立てた、または検証して結果が出た
  - 予想と異なる結果・エラーに遭遇した
  - 外部調査(ドキュメント・Web・コード読解)で事実を確認した
  - 計画・方針を変更した
- 記録するのは行動ログではなく推論: 計画 / 仮説と検証結果 / 発見 / 判断とその理由 / 失敗から得た知識。
- ノートは二部構成を保つ: 冒頭の「現在の状態と次の一手」は常に上書きして簡潔に
  最新化する(次の判断に必要な状態)。それ以降の推論の記録は追記する。
- 作業再開時・compaction 後は、続きを始める前に担当タスクのノートを読む。
  過去タスクの経緯は `docs/worklog/index.md` から辿る。
- タスク完了時、担当タスクのノートを OKF 形式で `docs/worklog/YYYY-MM-DD-<topic>.md`
  へ移し、`docs/worklog/index.md` に 1 行追記し、そのノートファイルを削除する。
  完了時はこの手順が「追記する」ルールより優先される。
```

## エッジケースの扱い

- **トピック名の衝突**: 別タスクなのに同名を選んだ場合。ノート冒頭の「目的」を読めば
  別タスクと分かるため、その場合は別名で作り直す、とルールに含めない(発生時に
  エージェントが判断できる自明な操作であり、ルールの肥大を避ける)。
- **同じタスクを複数セッションで開く**: 本設計の対象外(運用形態の確認で「別タスク
  並行」が前提)。同名ノートを共有する形になり、上書き競合は従来と同様に起きうる。
- **空の `working-notes/`**: ノートが 1 つもない状態は正常(進行中タスクなし)。

## 検証方法

1. 単体テスト: `python3 tests/test_pre_compact.py` が鮮度警告なしの実装で全件通る。
2. Codex CLI 実機で 2 セッションを同一ディレクトリで起動し、別タスクを進めて観察する:
   (a) 各セッションが自分の `working-notes/<topic>.md` だけを更新し、相互に潰さない、
   (b) 片方のタスク完了時に、そのノートだけが worklog へ移り削除される、
   (c) セッション再起動後、AGENTS.md ルールにより担当ノートを読んで再開できる。
3. hooks.json から SessionStart を外した状態で Codex CLI が警告なく起動する。
