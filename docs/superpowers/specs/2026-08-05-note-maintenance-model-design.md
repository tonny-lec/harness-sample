# 設計: working-note の維持モデルのセクション更新型への改訂

[working-notes 複数セッション対応の設計](2026-08-04-multi-session-working-notes-design.md)、
[記録・検索ルールの発火保証の設計](2026-08-05-rule-firing-reinforcement-design.md)、

## 背景と課題

実機運用で次の症状が観測された。

- 1 ターンが長い長時間実行時、複数の推論(仮説検証・調査)が 1 つの working-note に
  時系列で追記され続け、ノートが際限なく成長する。
- 冒頭「現在の状態と次の一手」の上書きは機能するが、本体が追記型のため追記部分が
  支配的になり、ノートは行動ログに近い時系列ストリームへ退化する。確定した事実・
  生きている仮説・棄却済み仮説・現在の計画が追記の海に埋もれ、取り出せない。

これは原設計が明確に否定した状態である。原設計(2026-08-01)は「全量追記だけでは
重要情報が埋もれる。**必要なのは保存量の最大化ではなく『次の判断に必要な状態』の
維持**」と規定した。「全履歴を残す」と「記憶を維持する」は違う。出典記事も、保持
すべきもの(発見したルール・目標・棄却マーク付きの失敗仮説・現在の計画・進行状況)と
削減すべきもの(繰り返しの観察データ・冗長な推論)を明確に分けており、性能向上は
「圧縮・構造化された推論の記憶の維持」から来ている。

根本原因: **ノートの維持モデルが「追記」で定義されている**。

- AGENTS.md「それ以降の推論の記録は追記する」— 二部構成の本体が追記型。
- リマインダー手順 2「そのノートに現在の状態と直近の判断・検証結果を追記する(数行)」—
  3 分ごとに時系列追記を機械的に促し、退化を強化する。さらに「現在の状態…を追記する」は
  AGENTS.md の「現在の状態は上書き」と矛盾している。

短いタスクでは完了時の蒸留(memory への統合とノート削除)が早く訪れるため追記型でも
破綻しないが、長いターンでは蒸留までの距離が長く、追記の蓄積がノートの検索性・
再読コストを悪化させる。

## 決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| 維持モデル | 時系列追記を廃止し、**セクション更新**で維持する | ノートは「エージェント自前の retained reasoning」であり、アーカイブではない。出典の compaction と同じ原理(関連情報を保持する短い表現への圧縮)をノートの平時運用に適用する |
| 維持の基準 | **「次の判断に必要な状態」の維持**。保存量を最大化しない | 原設計の規定の再確認。ノートの唯一の目的であり、セクションの取捨・圧縮の判断基準になる |
| ノート構造 | 冒頭「現在の状態と次の一手」(上書き)+ 内容ガイドと同じ見出しの 4 セクション: 仮説と検証結果 / 発見 / 判断とその理由 / 確定した事実と知識。空のセクションは書かない | 見出しを AGENTS.md 内容ガイド・docs/memory/ の記憶ファイルと同一にすることで、完了時の蒸留が「セクションを対応する記憶へ写す」操作になり、統合の品質が上がる |
| セクションの更新規約 | 冒頭は常に上書き。仮説は検証結果が出たら「確定」または「棄却(理由付き)」へ書き換える。発見・判断・事実は該当セクションへ追加し、冗長になったら短い表現へ圧縮・統合する | 出典の保持対象(棄却マーク付き仮説・判断と理由)と削減対象(冗長な推論)の区分をそのまま規約化する。削除ではなく圧縮とするのは、完了時の蒸留対象を失わないため |
| リマインダー文言 | 手順 2 のみ差し替え: 「そのノートを更新する: 冒頭の「現在の状態と次の一手」を上書きし、直近の判断・検証結果を該当セクションに反映する(数行)」 | 「追記」の語が退化を機械的に強化していた。上書き規約との矛盾も解消する。手順 1・3 と末尾の統合時期の文は不変 |
| compaction 関連 | **変更しない**(pre_compact / post_compact / スナップショット / compaction 後の再読ルール) | ユーザー判断: compaction は現状課題に感じていない。スコープをノートの維持モデルに絞る |
| 完了時の統合 | 変更しない(タスク完了時に memory へ統合しノート削除)。字句のみ「『追記する』ルールより優先」→「『更新する』ルールより優先」へ追従 | 中間蒸留(ターン中の memory 統合)は採らない。進行中タスクの推論はターン中はノートに居るべきで、memory はタスク横断の長期記憶。リマインダー文言改訂が抑止した「前倒し統合」とも整合する |
| hooks ロジック | 変更しない(閾値・クールダウン・発火条件・matcher すべて不変) | 文言の問題であり機構の問題ではない(リマインダー文言改訂と同じ判断) |
| テスト | `reminder_emitted` の固定部分一致に「そのノートを更新する」を追加 | 旧文言(追記指示)への退行をテストで検知する(リマインダー文言改訂のテスト方針を踏襲) |

## 採らなかった案

- **肥大時のみノート内圧縮を促す(行数閾値でリマインダー拡張)**: 平時は追記型の
  退化が進み続け、圧縮という重い割り込みが周期的に入る。維持モデル自体を直すほうが
  根本対処になる。
- **完結済み推論のターン中の memory への中間蒸留**: 層の役割(ノート = 進行中の
  ワーキングメモリ / memory = タスク横断の長期記憶)を混ぜる。知識整理モード誘発の
  実機観測(リマインダー文言改訂の背景)とも衝突する。
- **推論スレッド単位のノート分割**: 「スレッドが完結したか」の判定は自己監視型
  トリガーそのもので、長いターンで発火しないことが確定済みの事実(rule-firing 設計)。

## AGENTS.md の新ルール文面

「推論の外部化」の二部構成の箇条書きを次に置き換える(他の箇条書きは不変。
完了時ルールは「追記する」→「更新する」の字句追従のみ):

```markdown
- ノートは冒頭「現在の状態と次の一手」と、内容ガイドと同じ見出しのセクション
  (仮説と検証結果 / 発見 / 判断とその理由 / 確定した事実と知識)で構成する。
  維持の基準は保存量の最大化ではなく「次の判断に必要な状態」の維持。
  記録は時系列の追記ではなくセクションの更新で行う: 冒頭は常に上書きして
  簡潔に最新化する。仮説は検証結果が出たら「確定」または「棄却(理由付き)」へ
  書き換える。発見・判断・事実は該当セクションへ追加し、冗長になったら
  短い表現へ圧縮・統合する。空のセクションは書かない。
```

## 新しい注入文言(REMINDER 定数、手順 2 のみ変更)

```text
working-notes/ の担当ノートが 3 分以上更新されていません。次の手順を実行してください:
1. 現在のタスク専用のノート `working-notes/<topic>.md` があるか確認し、なければ作成する(別タスクのノートを流用しない)
2. そのノートを更新する: 冒頭の「現在の状態と次の一手」を上書きし、直近の判断・検証結果を該当セクションに反映する(数行)
3. 中断していた作業を再開する

docs/memory/ への統合はタスク完了時に行う。
```

## エッジケースの扱い

- **既存の追記型ノートが残っている場合**: 次にそのノートを更新するとき、新構造へ
  整理してから続ける(現在 `working-notes/` は空のため、実質的な移行作業はない。
  一度きりの操作に機構を作らない)。
- **累積セクション(発見・判断・事実)の肥大**: 「冗長になったら圧縮・統合」の規約で
  抑える。機械的な行数上限は設けない(memory 設計の「機械的な行数上限は設けない」と
  同じ判断)。
- **時系列の経緯の喪失**: ノート内から判断の時系列は失われる。価値の中心は経緯の
  順序ではなく判断・理由・知識であり(出典の削減対象の区分)、生ログは
  compaction-snapshots が保険として残る(現状維持)。
- **セクション更新の編集コスト**: 追記より 1 回あたりのコストが高いが、肥大ノートの
  再読・再解釈コストの削減で回収する(出典の実績: 圧縮維持で総トークン 1/6)。

## 検証方法

1. 単体テスト: `python3 tests/test_post_tool_use.py` が全件 green(アサーション追加後)。
   `python3 tests/test_pre_compact.py` も green のまま(hooks ロジック無変更の確認)。
2. 文言確認: hook を手で実行し、注入 JSON に新手順 2(更新: 上書き + セクション反映)が
   入ることを確認する。
3. 実機(次回の長時間タスクで観察):
   (a) ノートがセクション更新で維持され、時系列ログ化しない、
   (b) 仮説が検証結果(確定 / 棄却)へ書き換わる、
   (c) リマインダー後も追記型へ退行しない、
   (d) 完了時に構造化ノートから memory への統合が見出し対応で行われる。
