# 設計: working-note の維持モデルの改訂(状態の分離とセクション更新型への移行)

日付: 2026-08-05(改訂: 2026-08-06 状態ファイルの分離を追加)
先行設計: [状態外部化の設計](2026-08-01-state-externalization-design.md)、
[working-notes 複数セッション対応の設計](2026-08-04-multi-session-working-notes-design.md)、
[記録・検索ルールの発火保証の設計](2026-08-05-rule-firing-reinforcement-design.md)、
[リマインダー文言の手順型改訂](2026-08-05-reminder-wording-design.md)
出典(プロジェクトの起源): OpenAI「How enabling two settings tripled our scores on the
ARC-AGI-3 benchmark」<https://openai.com/index/how-two-settings-tripled-our-arc-agi-3-scores/>

## 背景と課題

実機運用で次の症状が観測された。

- 1 ターンが長い長時間実行時、複数の推論(仮説検証・調査)が 1 つの working-note に
  時系列で追記され続け、ノートが際限なく成長する。
- 冒頭「現在の状態と次の一手」の上書きは機能するが、本体が追記型のため追記部分が
  支配的になり、ノートは行動ログに近い時系列ストリームへ退化する。確定した事実・
  生きている仮説・棄却済み仮説・現在の計画が追記の海に埋もれ、取り出せない。

これは原設計が明確に否定した状態である。原設計(2026-08-01)は「全量追記だけでは
重要情報が埋もれる。**必要なのは保存量の最大化ではなく『次の判断に必要な状態』の
維持**」と規定した。「全履歴を残す」と「記憶を維持する」は違う。出典記事も、保持
すべきもの(発見したルール・目標・棄却マーク付きの失敗仮説・現在の計画・進行状況)と
削減すべきもの(繰り返しの観察データ・冗長な推論)を明確に分けており、性能向上は
「圧縮・構造化された推論の記憶の維持」から来ている。

根本原因: **ノートの維持モデルが「追記」で定義されている**。

- AGENTS.md「それ以降の推論の記録は追記する」— 二部構成の本体が追記型。
- リマインダー手順 2「そのノートに現在の状態と直近の判断・検証結果を追記する(数行)」—
  3 分ごとに時系列追記を機械的に促し、退化を強化する。さらに「現在の状態…を追記する」は
  AGENTS.md の「現在の状態は上書き」と矛盾している。

短いタスクでは完了時の蒸留(memory への統合とノート削除)が早く訪れるため追記型でも
破綻しないが、長いターンでは蒸留までの距離が長く、追記の蓄積がノートの検索性・
再読コストを悪化させる。

あわせて、出典との対応関係を見直すと、従来の二部構成は性質の異なる 2 つの情報を
1 ファイルに同居させていた。「現在の状態と次の一手」は進行の**要約**(常に上書き・
極小)であり、推論ではない。一方、次の一手を支える仮説・発見・判断・知識こそが
retained reasoning であり、working-note の本体に当たる。同居させる限り、追記部分の
成長が状態の可読性を圧迫する構造は残る。

## 決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| 状態の分離 | 「現在の状態と次の一手」を状態ファイル `working-notes/<topic>.state.md` へ分離する。ノート `working-notes/<topic>.md` は推論のみを持つ | 次の一手の推論(retained reasoning)がノートの本体であり、状態は進行の要約で性質が異なる。物理分離により「上書き」と「セクション更新」の意味論がファイル単位で分かれ、ノートの成長が状態の可読性を損なわない。復元時はまず極小の状態ファイルだけで再開できる |
| 状態ファイルの内容 | 目的 / 状態 / 決定 / 次の一手 の 4 項目の箇条書きのみ。常に上書きして簡潔に保つ | 従来の冒頭セクションと同じ内容・同じ上書き規約。ファイル全体が上書き対象になるため「追記で埋もれる」余地が構造的になくなる |
| ノートの維持モデル | 時系列追記を廃止し、**セクション更新**で維持する | ノートは「エージェント自前の retained reasoning」であり、アーカイブではない。出典の compaction と同じ原理(関連情報を保持する短い表現への圧縮)をノートの平時運用に適用する |
| 維持の基準 | **「次の判断に必要な状態」の維持**。保存量を最大化しない | 原設計の規定の再確認。取捨・圧縮の判断基準になる |
| ノート構造 | 内容ガイドと同じ見出しの 4 セクション: 仮説と検証結果 / 発見 / 判断とその理由 / 確定した事実と知識。空のセクションは書かない | 見出しを AGENTS.md 内容ガイド・docs/memory/ の記憶ファイルと同一にすることで、完了時の蒸留が「セクションを対応する記憶へ写す」操作になり、統合の品質が上がる |
| セクションの更新規約 | 仮説は検証結果が出たら「確定」または「棄却(理由付き)」へ書き換える。発見・判断・事実は該当セクションへ追加し、冗長になったら短い表現へ圧縮・統合する | 出典の保持対象(棄却マーク付き仮説・判断と理由)と削減対象(冗長な推論)の区分をそのまま規約化する。削除ではなく圧縮とするのは、完了時の蒸留対象を失わないため |
| リマインダー文言 | 手順 1 を状態ファイルとノートの 2 ファイル確認へ、手順 2 を「状態ファイルを上書きで最新化し、直近の判断・検証結果をノートの該当セクションに反映する(数行)」へ差し替え | 「追記」の語が退化を機械的に強化していた。分離後の 2 ファイル運用を手順として明示する。手順 3 と末尾の統合時期の文は不変 |
| hooks ロジック | 変更しない(閾値・クールダウン・発火条件・matcher・glob すべて不変) | `Path.glob("*.md")` は `<topic>.state.md` にもマッチするため(確認済み)、状態ファイルの上書きだけでも鮮度判定が更新され、分離によるロジック変更は不要 |
| compaction 関連 | 変更しない(pre_compact / post_compact / スナップショット)。「compaction 後に読む」対象の字句のみ状態ファイルへ追従 | ユーザー判断: compaction は現状課題に感じていない。スコープをノートの維持モデルに絞る |
| 完了時の統合 | ノートの知見を memory へ統合する規約は変更しない。削除対象を「状態ファイルとノートの両方」へ追従 | 中間蒸留(ターン中の memory 統合)は採らない。進行中タスクの推論はターン中はノートに居るべきで、memory はタスク横断の長期記憶。リマインダー文言改訂が抑止した「前倒し統合」とも整合する |
| テスト | `reminder_emitted` の固定部分一致に「状態ファイルを上書き」を追加 | 旧文言(追記指示)への退行をテストで検知する(リマインダー文言改訂のテスト方針を踏襲) |

## 採らなかった案

- **1 ファイルのままセクション更新型へ改訂(本設計の初版)**: 上書き部分と更新部分が
  同居する限り、追記部分の成長が状態の可読性を圧迫する構造が残る。分離のほうが
  意味論が明確で、復元時の読み取りも小さくなる。
- **タスクごとのサブディレクトリ(`working-notes/<topic>/state.md` + `note.md`)**:
  hook の鮮度判定 `glob("*.md")` が直下しか見ないため、hook のロジック変更が必要に
  なる。フラットな 2 ファイルなら変更ゼロで済む。
- **肥大時のみノート内圧縮を促す(行数閾値でリマインダー拡張)**: 平時は追記型の
  退化が進み続け、圧縮という重い割り込みが周期的に入る。維持モデル自体を直すほうが
  根本対処になる。
- **完結済み推論のターン中の memory への中間蒸留**: 層の役割(ノート = 進行中の
  ワーキングメモリ / memory = タスク横断の長期記憶)を混ぜる。知識整理モード誘発の
  実機観測(リマインダー文言改訂の背景)とも衝突する。
- **推論スレッド単位のノート分割**: 「スレッドが完結したか」の判定は自己監視型
  トリガーそのもので、長いターンで発火しないことが確定済みの事実(rule-firing 設計)。

## AGENTS.md の新ルール文面

「推論の外部化」セクション全体を次に置き換える(grep・memory index 確認・完了時の
統合手順の各箇条書きは従来の内容を維持し、ファイル参照のみ追従):

```markdown
## 推論の外部化

- タスク開始時に `working-notes/` を確認する。担当タスクの状態ファイル
  `working-notes/<topic>.state.md` とノート `working-notes/<topic>.md` が
  あれば読んで再開し、なければ作成する(`<topic>` は短いケバブケース)。
  他タスクのファイルは読んでよいが、編集しない。
- タスク開始時に `docs/memory/index.md` で関連カテゴリを確認する。
- コマンド・テスト・検証を実行して結果を確認した直後、状態ファイルを上書きで
  最新化し、その時点の推論をノートの該当セクションへ反映する。タスクの大小を
  問わない。記録するのは行動ログではなく推論: 仮説と検証結果(予想と合って
  いたか)/ 発見 / 判断とその理由(採らなかった案を含む)/ 確定した事実と知識
  (不確実だったことが検証で確定したら、成功・失敗を問わず書く。
  自明な成功は書かない)。
- ノートに記録するとき、同じトピックのキーワードで `docs/memory/` を
  grep し、関連する記憶があれば読む。未知の領域・予想外の結果に直面した
  ときも同様に grep する。
- 状態ファイルは 目的 / 状態 / 決定 / 次の一手 の箇条書きだけを常に上書きで
  簡潔に保つ(次の判断に必要な状態)。ノートは内容ガイドと同じ見出しの
  セクション(仮説と検証結果 / 発見 / 判断とその理由 / 確定した事実と知識)で
  構成し、時系列の追記ではなくセクションの更新で維持する。維持の基準は
  保存量の最大化ではなく「次の判断に必要な状態」の維持。仮説は検証結果が
  出たら「確定」または「棄却(理由付き)」へ書き換える。発見・判断・事実は
  該当セクションへ追加し、冗長になったら短い表現へ圧縮・統合する。
  空のセクションは書かない。
- 作業再開時・compaction 後は、続きを始める前に担当タスクの状態ファイルを読み、
  必要に応じてノートを読む。
- タスク完了時、担当タスクのノートの知見を `docs/memory/` の記憶へ統合する:
  同トピックの記憶があれば既存ファイルを更新して `generated.at` を最新化し、
  なければカテゴリを選んで `docs/memory/<category>/<topic>.md` を新規作成する
  (合うカテゴリがなければ新設し、ルート `index.md` にカテゴリを追記する)。
  該当カテゴリの `index.md` を更新し、状態ファイルとノートを削除する。
  完了時はこの手順が「更新する」ルールより優先される。
```

(従来の内容ガイドにあった「計画」は状態ファイルの「決定・次の一手」と重複するため
内容ガイドから外す。docs/memory/ の記憶ファイル側の見出し規約は変更しない。)

## 新しい注入文言(REMINDER 定数)

```text
working-notes/ の担当ノートが 3 分以上更新されていません。次の手順を実行してください:
1. 現在のタスク専用の状態ファイル `working-notes/<topic>.state.md` とノート `working-notes/<topic>.md` があるか確認し、なければ作成する(別タスクのファイルを流用しない)
2. 状態ファイルを上書きで最新化し、直近の判断・検証結果をノートの該当セクションに反映する(数行)
3. 中断していた作業を再開する

docs/memory/ への統合はタスク完了時に行う。
```

テストが検査する固定部分(「working-notes/ の担当ノート」「次の手順を実行して
ください」)は 1 行目に残る。退行検知の固定部分一致は「状態ファイルを上書き」とする。

## エッジケースの扱い

- **既存の追記型ノートが残っている場合**: 次にそのノートを更新するとき、状態ファイル
  を切り出して新構造へ整理してから続ける(現在 `working-notes/` は空のため、実質的な
  移行作業はない。一度きりの操作に機構を作らない)。
- **状態ファイルとノートの片方だけが存在する**: 次の記録アンカー(結果確認直後)で
  欠けている方を作る。リマインダー手順 1 も両ファイルの確認を含むため補強される。
- **状態ファイルだけが更新され続け、ノートに推論が反映されない**: 鮮度判定は
  どちらの更新でも静音化するため、hook はこの偏りを検知しない。記録アンカーの
  ルール(状態の上書きとノートへの反映を 1 つの手順にする)で防ぎ、実機観察で
  兆候が見えたら対策を再検討する。
- **累積セクション(発見・判断・事実)の肥大**: 「冗長になったら圧縮・統合」の規約で
  抑える。機械的な行数上限は設けない(memory 設計の「機械的な行数上限は設けない」と
  同じ判断)。
- **時系列の経緯の喪失**: ノート内から判断の時系列は失われる。価値の中心は経緯の
  順序ではなく判断・理由・知識であり(出典の削減対象の区分)、生ログは
  compaction-snapshots が保険として残る(現状維持)。
- **セクション更新の編集コスト**: 追記より 1 回あたりのコストが高いが、肥大ノートの
  再読・再解釈コストの削減で回収する(出典の実績: 圧縮維持で総トークン 1/6)。

## 検証方法

1. 単体テスト: `python3 tests/test_post_tool_use.py` が全件 green(アサーション追加後)。
   `python3 tests/test_pre_compact.py` も green のまま(hooks ロジック無変更の確認)。
2. 文言確認: hook を手で実行し、注入 JSON に新手順(2 ファイル確認 → 状態上書き +
   セクション反映 → 再開)が入ることを確認する。
3. glob の確認: `working-notes/<topic>.state.md` だけを更新した状態で hook を実行し、
   鮮度判定が静音化することを確認する(`glob("*.md")` のマッチの実証)。
4. 実機(次回の長時間タスクで観察):
   (a) 状態ファイルが極小のまま上書き維持され、ノートがセクション更新で維持されて
   時系列ログ化しない、
   (b) 仮説が検証結果(確定 / 棄却)へ書き換わる、
   (c) リマインダー後も追記型へ退行しない、
   (d) 完了時に構造化ノートから memory への統合が見出し対応で行われ、状態ファイルと
   ノートの両方が削除される。
