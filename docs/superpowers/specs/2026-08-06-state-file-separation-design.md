# 設計: 状態ファイルの分離(「現在の状態と次の一手」の working-note からの独立)

日付: 2026-08-06
先行設計: [状態外部化の設計](2026-08-01-state-externalization-design.md)、
[working-notes 複数セッション対応の設計](2026-08-04-multi-session-working-notes-design.md)、
[記録・検索ルールの発火保証の設計](2026-08-05-rule-firing-reinforcement-design.md)、
[リマインダー文言の手順型改訂](2026-08-05-reminder-wording-design.md)

出典(プロジェクトの起源): OpenAI「How enabling two settings tripled our scores on the

## 背景と課題

実機運用で次の症状が観測された: 1 ターンが長い長時間実行時、1 つの working-note に
推論が時系列で追記され続けてノートが際限なく成長し、冒頭の「現在の状態と次の一手」が
追記の海に埋もれていく。

原設計(2026-08-01)は「全量追記だけでは重要情報が埋もれる。**必要なのは保存量の
最大化ではなく『次の判断に必要な状態』の維持**」と規定した。「全履歴を残す」と
「記憶を維持する」は違う。この基準で症状を分析すると、問題は追記そのものではなく
次の 2 つにある。

1. **性質の異なる 2 つの情報が 1 ファイルに同居している**。「現在の状態と次の一手」は
   進行の**要約**(常に上書き・極小)であり、推論ではない。一方、次の一手を支える
   仮説・発見・判断・知識こそが retained reasoning(出典記事の教訓)であり、
   working-note の本体に当たる。同居させる限り、推論の追記が成長するほど状態の
   可読性が圧迫される構造が残る。
2. **リマインダー文言が状態の「追記」を指示している**。手順 2「そのノートに現在の
   状態と直近の判断・検証結果を追記する(数行)」は、AGENTS.md の「現在の状態は
   上書き」と矛盾しており、3 分ごとに時系列追記を機械的に促して退化を強化する。

一方、推論の記録そのものが追記型であることは原設計の仕様どおりであり、変更しない。
判断の経緯を保全する追記型の利点は残し、完了時の蒸留(memory への統合)が再構成を
担う(memory 設計は「統合時に時系列のまま連結せず知見単位の再構成を許容」と規定済み)。

## 決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| 状態の分離 | 「現在の状態と次の一手」を状態ファイル `working-notes/<topic>.state.md` へ分離する。ノート `working-notes/<topic>.md` は推論の記録のみを持つ | 状態は進行の要約、ノートは retained reasoning で性質が異なる。物理分離により「上書き」と「追記」の意味論がファイル単位で分かれ、ノートがどれだけ育っても状態の可読性が損なわれない。復元時はまず極小の状態ファイルだけで再開できる |
| 状態ファイルの内容 | 目的 / 状態 / 決定 / 次の一手 の 4 項目の箇条書きのみ。常に上書きして簡潔に保つ | 従来の冒頭セクションと同じ内容・同じ上書き規約。ファイル全体が上書き対象になるため「追記で埋もれる」余地が構造的になくなる |
| ノートの仕様 | **変更しない**。推論の記録として追記型を維持し、内容ガイド(計画 / 仮説と検証結果 / 発見 / 判断とその理由 / 確定した事実と知識)も不変 | 追記型は判断の経緯の保全という原設計の意図どおり。埋もれの問題は状態の分離で解消する。ノートの再構成は完了時の蒸留が担う(memory 設計で規定済み)。仕様変更を状態の分離だけに絞ることで、変更面積と退行リスクを最小にする |
| 記録アンカー | 変更しない(コマンド・テスト・検証の結果確認直後)。動作を「状態ファイルを上書きで最新化し、その時点の推論をノートに追記する」に読み替える | アンカーの有効性は rule-firing 設計で確立済み。変わるのは「状態の上書き」の宛先が別ファイルになることだけ |
| リマインダー文言 | 1 行目を「担当タスクのファイル」へ、手順 1 を 2 ファイルの確認へ、手順 2 を「状態ファイルを上書きで最新化し、直近の判断・検証結果をノートに追記する(数行)」へ改める | 状態の分離により「追記」の指示が推論の記録(追記型)にだけ向かい、上書き規約との矛盾が構造的に解消する。鮮度判定は 2 ファイルいずれの mtime も対象になるため 1 行目も実態に合わせる。手順 3 と末尾の統合時期の文は不変(reminder-wording 設計の手順型構造・語気排除の方針を踏襲) |
| hooks ロジック | 変更しない(閾値・クールダウン・発火条件・matcher・glob すべて不変) | `Path.glob("*.md")` は `<topic>.state.md` にもマッチするため(実行確認済み)、状態ファイルの上書きだけでも鮮度判定が更新され、分離によるロジック変更は不要 |
| post_tool_use.py の docstring | 「ノートの確認・追記・作業再開」の字句を新手順(確認・状態の上書きと追記・再開)へ追従 | docstring と REMINDER の不一致は過去に修正済みの既知の問題類型(0404e09)。同じ轍を踏まない |
| post_compact.py の通知文言 | 「担当タスクのノート(working-notes/<topic>.md)を読み直して」→「担当タスクの状態ファイル(working-notes/<topic>.state.md)を読み直して」へ字句のみ追従 | compaction の機構(退避・通知のみ)は不変。通知が指すファイルが分離後の一次復元元(状態ファイル)とずれると誤誘導になるため、文言だけ追従する |
| compaction 関連の機構 | 変更しない(pre_compact / スナップショット / 発火条件) | ユーザー判断: compaction は現状課題に感じていない。スコープを状態の分離に絞る |
| 完了時の統合 | ノートの知見を memory へ統合する規約は変更しない。削除対象を「状態ファイルとノートの両方」へ追従。優先関係は維持しつつ、対象を「平時の記録ルール(状態ファイルの上書きとノートへの追記)」と明示する | 中間蒸留(ターン中の memory 統合)は採らない。進行中タスクの推論はターン中はノートに居るべきで、memory はタスク横断の長期記憶。リマインダーが規定する「統合はタスク完了時」とも整合する |
| テスト | (a) `reminder_emitted` の固定部分一致を新文言(「working-notes/ の担当タスクのファイル」「次の手順を実行してください」「上書きで最新化」)へ更新、(b) 状態ファイルだけが新鮮なケースで沈黙するテストを追加 | (a) 旧文言(状態の追記指示)への退行を検知する(reminder-wording 設計のテスト方針を踏襲)。(b) glob が `.state.md` を拾うことを実機任せにせず単体テストで固定する |
| AGENTS.md の文面リファクタリング | 冒頭で用語(状態ファイル / ノート)と各ファイルの役割を定義し、`docs/memory/` 参照のトリガーを 3 つ(タスク開始時 / 行動・判断の前 / ノートへ追記する前)に分離し、各ルールに目的(〜ため)を付す | 2 ファイル化で「ノート」の指示対象が曖昧になる。旧文面は記録時 grep と未知領域遭遇時 grep という別事象を 1 ルールに混在させ、読んだ記憶をどう使うのかも示していなかった。ルールは実行者に意図が伝わってはじめて正しく発火する。記録アンカーへの grep の相乗り(rule-firing 設計の決定)は無条件のまま維持する |

## 先行設計からの改訂点の整理

- **原設計(2026-08-01)「ノートの構造: 二部構成」**: 二部構成の 2 つの役割
  (状態の維持 / 経緯の保全)と各部の規約(上書き / 追記)はそのまま維持し、
  実現手段だけを「1 ファイル内の 2 セクション」から「状態ファイル + ノートの
  2 ファイル」へ改める。
- **複数セッション対応(2026-08-04)「ノートの単位: タスクごとに 1 ファイル」**:
  「タスクごと」の鍵(topic)は維持し、1 タスク 1 ファイルを 1 タスク 2 ファイル
  (状態 + ノート)へ改める。発見・再開・完了・他タスク不干渉の各ルールは
  2 ファイルへ読み替えて維持する。同 spec の「ノートの単位」「ノート内部構造」行に
  本設計への改訂参照を 1 行注記する。
- **リマインダー文言の手順型改訂(2026-08-05)「注入文言」**: 手順型 3 ステップ +
  統合時期の平叙文という構造は維持し、手順 1・2 の内容を 2 ファイル構成へ差し替える。
  同 spec の「新しい注入文言」節に本設計への改訂参照を 1 行注記する
  (matcher 改訂と同じ流儀)。

## 採らなかった案

- **ノートをセクション更新型(仮説の書き換え・冗長時の圧縮統合)へ改訂する
  (本設計の検討過程の案)**: 「冗長になったら圧縮する」は自己監視型トリガーで、
  長いターンで発火しないことが確定済みの事実(rule-firing 設計)に反する。また
  ノートの再構成は完了時の蒸留が既に担っており、平時に前倒しする必要がない。
  状態の分離だけで「埋もれ」の問題は解消するため、仕様変更の面積を広げない。
- **1 ファイル二部構成のまま文言だけ直す**: リマインダーの矛盾は解消できるが、
  推論の追記が成長するほど状態セクションの可読性が圧迫される構造は残る。
- **タスクごとのサブディレクトリ(`working-notes/<topic>/state.md` + `note.md`)**:
  hook の鮮度判定 `glob("*.md")` が直下しか見ないため、hook のロジック変更が必要に
  なる。フラットな 2 ファイルなら変更ゼロで済む。
- **完結済み推論のターン中の memory への中間蒸留**: 層の役割(ノート = 進行中の
  ワーキングメモリ / memory = タスク横断の長期記憶)を混ぜる。知識整理モード誘発の
  実機観測(リマインダー文言改訂の背景)とも衝突する。
- **推論スレッド単位のノート分割**: 「スレッドが完結したか」の判定は自己監視型
  トリガーそのもので、長いターンで発火しない(同上)。

## AGENTS.md の新ルール文面

「推論の外部化」セクション全体を次に置き換える。構成は「前提(何を・どこに・
なぜ置くか)→ 用語の定義 → トリガーごとのルール(各ルールに目的を付す)」とする:

```markdown
## 推論の外部化

作業状態は会話履歴ではなくファイルに置く。compaction やセッションの中断で会話が
失われても、ファイルから同じ地点へ復帰するためである。タスクごとに次の 2 ファイルを
`working-notes/` に置く(`<topic>` は短いケバブケース):

- **状態ファイル** `working-notes/<topic>.state.md` — 進行の要約。目的 / 状態 /
  決定 / 次の一手 の箇条書きだけを常に上書きで簡潔に保ち、履歴は持たせない
  (維持するのは保存量ではなく「次の判断に必要な状態」)。
- **ノート** `working-notes/<topic>.md` — 推論の記録。追記で育てる。記録するのは
  行動ログではなく推論: 計画 / 仮説と検証結果(予想と合っていたか)/ 発見 /
  判断とその理由(採らなかった案を含む)/ 確定した事実と知識(不確実だったことが
  検証で確定したら、成功・失敗を問わず書く。自明な成功は書かない)。

ルール:

- タスク開始時、`working-notes/` を確認する。担当タスクの状態ファイルとノートが
  あれば読んで続きから再開し、なければ作成する。他タスクのファイルは読んでよいが、
  編集しない(並行する他セッションの状態を壊さないため)。
- タスク開始時、`docs/memory/index.md` で関連カテゴリを確認し、関連する記憶が
  あれば読んでから着手する(過去タスクで確定した知識を再利用し、同じ調査・
  同じ失敗を繰り返さないため)。
- 作業中に未知の領域へ入るとき・技術的な判断を下すとき・予想外の結果に直面した
  ときは、次の行動の前にそのトピックのキーワードで `docs/memory/` を grep し、
  関連する記憶があれば読む(既知の事実と過去の失敗を判断材料に加えるため)。
- コマンド・テスト・検証を実行して結果を確認した直後、毎回次の 2 つを行う
  (タスクの大小を問わない):
  1. 状態ファイルを上書きで最新化する。
  2. その時点で新しく生まれた推論をノートへ追記する。追記する前に、そのトピックの
     キーワードで `docs/memory/` を grep し、関連する記憶があれば読む(発見が
     既存の記憶と重複・矛盾していないかを確かめるため。矛盾するときは、どちらが
     正しいか検証してから記録する)。
- 作業再開時・compaction 後は、続きを始める前に担当タスクの状態ファイルを読む。
  直前の経緯や判断理由が必要なときはノートも読む(会話履歴に頼らず状態を
  復元するため)。
- タスク完了時、担当タスクのノートの知見を `docs/memory/` の記憶へ統合する:
  同トピックの記憶があれば既存ファイルを更新して `generated.at` を最新化し、
  なければカテゴリを選んで `docs/memory/<category>/<topic>.md` を新規作成する
  (合うカテゴリがなければ新設し、ルート `index.md` にカテゴリを追記する)。
  該当カテゴリの `index.md` を更新し、状態ファイルとノートを削除する(進行中の
  状態は、記憶へ昇格した時点で役目を終えるため)。完了時はこの統合・削除の手順が、
  平時の記録ルール(状態ファイルの上書きとノートへの追記)より優先される。
```

旧文面からの主な変更(構造の変更を除く):

- 「ノートに記録するとき grep」と「未知の領域・予想外の結果に直面したとき grep」は
  別事象のため、2 つのルールへ分離した。前者は記録アンカーへの相乗り(rule-firing
  設計の決定)を無条件のまま維持し、目的を「発見と既存記憶の重複・矛盾の確認」と
  明示した。後者は行動・判断の**前**に読む先読みであり、目的を「既知の事実と失敗を
  判断材料に加える」と明示した。
- 「必要に応じてノートを読む」の曖昧さを「直前の経緯や判断理由が必要なとき」へ具体化した。
- 完了時の優先関係の対象を「平時の記録ルール(状態ファイルの上書きとノートへの追記)」と
  明示した(旧「『追記する』ルール」は指示対象が 1 箇条書きに限られ、状態ファイルの
  扱いが宙に浮くため)。

## 新しい注入文言(REMINDER 定数)

(改訂 2026-08-06: 手順 2 以降は[状態ファイル上書きの操作手順化](2026-08-06-state-overwrite-wording-design.md)で書き換え操作の 4 手順へ差し替えられた)

```text
working-notes/ の担当タスクのファイルが 3 分以上更新されていません。次の手順を実行してください:
1. 現在のタスク専用の状態ファイル `working-notes/<topic>.state.md` とノート `working-notes/<topic>.md` があるか確認し、なければ作成する(別タスクのファイルを流用しない)
2. 状態ファイル(目的 / 状態 / 決定 / 次の一手)を上書きで最新化し、直近の判断・検証結果をノートに追記する(数行)
3. 中断していた作業を再開する

docs/memory/ への統合はタスク完了時に行う。
```

## エッジケースの扱い

- **既存の旧構成ノートが残っている場合**: 次にそのノートを更新するとき、冒頭の
  「現在の状態と次の一手」を状態ファイルへ切り出してから続ける(現在
  `working-notes/` は空のため、実質的な移行作業はない。一度きりの操作に機構を
  作らない)。README の移行の 1 文も 2 ファイル構成へ読み替える。
- **状態ファイルとノートの片方だけが存在する**: 次の記録アンカー(結果確認直後)で
  欠けている方を作る。リマインダー手順 1 も両ファイルの確認を含むため補強される。
- **状態ファイルだけが更新され続け、ノートに推論が追記されない**: 鮮度判定は
  どちらの更新でも静音化するため、hook はこの偏りを検知しない。記録アンカーの
  ルール(状態の上書きとノートへの追記を 1 つの手順にする)で防ぎ、実機観察で
  兆候が見えたら対策を再検討する。
- **長いターンでのノートの成長**: 分離後も推論の記録は追記で成長する。これは仕様
  どおりの挙動として許容する。「次の判断に必要な状態」の維持は状態ファイルが担い、
  ノートの再構成は完了時の蒸留が担うため、成長は復元性を損なわない。完了時の蒸留
  コストが問題として観測されたら、その時点で対策を設計する。
- **topic 名の付け方**: `<topic>.state.md` と `<topic>.md` の対応はファイル名の規約
  のみで担保する(対応表などの機構は作らない)。

## 検証方法

1. 単体テスト: `python3 tests/test_post_tool_use.py` が全件 green(固定部分の更新と
   状態ファイルのみ新鮮ケースの追加後)。`python3 tests/test_pre_compact.py` も green の
   まま(hooks ロジック無変更の確認)。
2. 文言確認: post_tool_use.py と post_compact.py を手で実行し、出力 JSON に新文言が
   入ることを確認する。
3. 文書の整合: `grep -rn "二部構成" AGENTS.md README.md docs/state-lifecycle.md` が
   0 件になり、同 3 ファイルの `working-notes/<topic>.md` への言及がすべて 2 ファイル
   構成の文脈になっていることを確認する(過去の spec / plan / 記憶は対象外)。
4. 実機(次回の長時間タスクで観察):
   (a) 状態ファイルが極小のまま上書き維持され、ノートには推論だけが追記される、
   (b) リマインダー後に「状態の上書き + 数行追記 → 再開」となり、状態がノートへ
   追記されない、
   (c) compaction 後・再開時に状態ファイルから復帰する、
   (d) 完了時に memory への統合が行われ、状態ファイルとノートの両方が削除される。
