# 設計: 状態ファイル上書きの操作手順化(文言改訂)

日付: 2026-08-06
先行設計: [状態ファイル分離の設計](2026-08-06-state-file-separation-design.md)(本書はその文言の一部を改訂する)、
[リマインダー文言の手順型改訂](2026-08-05-reminder-wording-design.md)、
[記録・検索ルールの発火保証の設計](2026-08-05-rule-firing-reinforcement-design.md)

## 背景と課題

状態ファイル分離の導入後、実機(Codex CLI・改訂版導入済みの別プロジェクト・長時間
タスク)で次の症状が観測された: `working-notes/<topic>.state.md` が上書きされず
追記され続け、状態ブロックが積み重なって肥大する。分離前の症状(1 つの working-note
への推論の積み上がり)が、新しいファイルで再現した形になる。

根本原因はプロンプト層の指示にある。

1. **「上書きで最新化」は結果の状態を述べているだけで、操作を規定していない**。
   実機で確定済みの知見(e2e-verification)は「Codex は抽象語・語気ではなく
   『これをしたらこれ』という操作手順に高精度で従う」であり、「上書き」という
   結果の要求は操作手順になっていなかった。
2. **削除への明示的な許可がない**。上書きは既存行の削除を伴う。モデルは破壊的
   編集を避けるバイアスを持つため、許可が明示されない限り「末尾に最新ブロックを
   足す」ことで「最新化」を満たしたことにしてしまう。

対処方針は次の方法論に従う(本改訂の判断基準):

> 決定論化(機構による保証)は、非決定論的に成功例がある挙動の成功率を上げる
> ための手段である。一度も成功が観測されていない挙動を機構で包んでも、包む対象が
> 存在しない。

旧構造での「冒頭セクションの上書き」は実機検証で非決定論的に成功していた
(フェーズ 1 e2e (d))。新構造での「state.md 全体の書き換え」はまだ成功が観測されて
いない。したがって現在は機構化(hook による正規化・検知)を検討する段階ではなく、
**プロンプト層を操作レベルへ改訂し、まず非決定論的に成功させる段階**である。

## 決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| リマインダー手順 | 手順 2 を分割して 4 ステップ化する。手順 2 = 状態ファイルの書き換え操作(「内容全体を、現時点の 目的 / 状態 / 決定 / 次の一手 の 4 行の箇条書きだけに書き換える(前の内容は消してよい。末尾への追記はしない)」)、手順 3 = ノートへの追記、手順 4 = 再開 | 操作の規定(内容全体を〜だけに書き換える)、削除の明示的許可(消してよい)、禁止操作の明示(末尾への追記はしない)の 3 点を手順に組み込む。1 手順 1 操作に分けるのは手順型の精度を上げるため |
| AGENTS.md 記録アンカー | サブ手順 1 を「状態ファイルの内容全体を、現時点の 目的 / 状態 / 決定 / 次の一手 の 4 行の箇条書きだけに書き換える(前の内容は残さない)。」へ差し替え | リマインダーと同じ操作規定。ルールとリマインダーの二重表現の不一致を作らない |
| 状態ファイルの定義文 | 変更しない(「常に上書きで簡潔に保ち、履歴は持たせない」) | 定義は不変条件(意味論)の記述であり、操作の記述は各ルール・手順が担う。役割が異なる |
| hooks ロジック | 変更しない(閾値・クールダウン・発火条件・matcher・glob すべて不変)。変更は REMINDER 定数と docstring の字句のみ | 文言の問題であり機構の問題ではない(リマインダー文言改訂と同じ判断) |
| 機構化の保留 | hook による正規化・肥大検知は今回実装しない。実機で書き換えの成功が観測された後、長ターンでの成功率が不足する場合に限り検討する | 上記の方法論。成功例ゼロの段階での機構化は対象不在。成功率が十分ならそのまま不要(YAGNI) |
| テスト | `reminder_emitted` の固定部分一致「上書きで最新化」を「箇条書きだけに書き換える」へ更新 | 旧文言への退行検知を新文言に追従させる(従来のテスト方針を踏襲) |
| 追従文書 | 操作手順を記述している文のみ「書き換える」表現へ追従(README 導入手順 2 の記録の行、state-lifecycle §2 の記録の文とリマインダー説明の文)。概念として「上書き」と述べている箇所(仕組み表・定義の説明など)は変更しない | 操作の記述と意味論の記述を区別する(上記の定義文と同じ判断)。変更面積を最小にする |
| 先行 spec | 状態ファイル分離 spec の「新しい注入文言」節に本設計への改訂参照を 1 行注記する | 既存の流儀(リマインダー文言改訂・状態ファイル分離のときと同じ) |

## 新しい注入文言(REMINDER 定数)

```text
working-notes/ の担当タスクのファイルが 3 分以上更新されていません。次の手順を実行してください:
1. 現在のタスク専用の状態ファイル `working-notes/<topic>.state.md` とノート `working-notes/<topic>.md` があるか確認し、なければ作成する(別タスクのファイルを流用しない)
2. 状態ファイルの内容全体を、現時点の 目的 / 状態 / 決定 / 次の一手 の 4 行の箇条書きだけに書き換える(前の内容は消してよい。末尾への追記はしない)
3. 直近の判断・検証結果をノートに追記する(数行)
4. 中断していた作業を再開する

docs/memory/ への統合はタスク完了時に行う。
```

テストが検査する固定部分: 「working-notes/ の担当タスクのファイル」「次の手順を
実行してください」(不変)+「箇条書きだけに書き換える」(「上書きで最新化」から変更)。

## AGENTS.md の新文面(記録アンカーのサブ手順のみ)

```markdown
  1. 状態ファイルの内容全体を、現時点の 目的 / 状態 / 決定 / 次の一手 の
     4 行の箇条書きだけに書き換える(前の内容は残さない)。
```

## エッジケースの扱い

- **「4 行」と実態の不一致**: 項目のどれかが長く複数行に折り返される・一時的に
  「決定: なし」になるのは許容する(行数は目安であり、検査主体はモデル自身)。
  機械的な行数検査は導入しない(機構化の保留と同じ判断)。
- **文言改訂でも追記が続く場合**: 実機観測でなお失敗が支配的なら、プロンプト層の
  さらなる改訂(例: 書き換え操作の具体例の付記)を先に試し、成功例が出た後に
  機構化を検討する(方法論の順序を維持)。

## 検証方法

1. 単体テスト: `python3 tests/test_post_tool_use.py` が全件 green(固定部分更新後)。
   `python3 tests/test_pre_compact.py` も green のまま。
2. 文言確認: hook を手で実行し、注入 JSON に新 4 手順が入ることを確認する。
3. 実機(本改訂の本命の検証): 導入先プロジェクトで短〜中タスクを実行し、
   (a) state.md が 4 項目の箇条書きに保たれる(ブロックが積み重ならない)、
   (b) ノートには推論だけが追記される、を観測する。**成功が観測されたら**、
   長時間タスクでの成功率を観測し、不足する場合に限り機構化の設計に進む。
