# 設計: PostToolUse リマインダー文言の手順型への改訂

日付: 2026-08-05
先行設計: [記録・検索ルールの発火保証の設計](2026-08-05-rule-firing-reinforcement-design.md)(本書はその注入文言を改訂する)

## 背景と課題

リマインダー hook の実機検証(別 PC・長時間タスク)で、hook の発火自体は確認できた
(matcher `*`)。一方で、現行の注入文言に起因する副作用と、文言が前提にしている
状態の穴が観測・指摘された。

現行文言:

> リマインダー: working-notes/ の担当ノートが 3 分以上更新されていません。
> 直近の判断・検証結果をノートに記録し、関連する docs/memory/ を grep で
> 確認してください(AGENTS.md「推論の外部化」)。

問題点:

1. **知識整理モードの誘発**: 「記録 + grep」という 2 つの知識管理アクションを
   並べているため「いま知識整理の時間だ」と読め、作業途中に腰を据えたまとめを
   始める。記憶への統合(タスク完了時の作業)を前倒しで行う恐れもある。
2. **復帰指示の欠如**: 記録後に元の作業へ戻る指示がなく、リマインダー対応が
   自然な区切りに見えて作業へ復帰しない。
3. **前提の穴**: 「記録してください」はノートが正しく存在することを前提に
   している。実態には「ノート未作成」「別タスクのノートの使い回し」があり、
   追記の指示では対応できない。
4. **語気への過敏**: Codex は「すぐ」等の語気・含みのある言葉に敏感で余計な
   推論をする。強調ではなく「これをしたら次はこれ」という手順型の指示のほうが
   精度が高い(ユーザーの実機観察による知見)。

## 決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| 文言の形式 | 番号付き手順(3 ステップ)+ 統合時期の平叙の規定文 | 手順型は語気に頼らず行動を規定でき、Codex の余計な推論を誘発しない(問題点 4)。復帰は「手順 3」として構造に組み込み、そこで終わる余地をなくす(問題点 2) |
| 手順 1 の内容 | ノートの確認 → なければ作成(別タスクのノートを流用しない) | 未作成・使い回しの両方をカバーする(問題点 3)。「ノートなし = stale」という発火条件は既存のため、未作成ケースにも確実に届く |
| grep 言及 | 削除 | リマインダーを単一目的(ノートの健全化と復帰)に絞る。検索は AGENTS.md の「記録するとき grep」ルールが担い、記録さえ発火すれば相乗りで発火する建て付けは維持(問題点 1) |
| 統合時期の記載 | 「docs/memory/ への統合はタスク完了時に行う。」を末尾に平叙で置く | 前倒し統合の防止(問題点 1)。禁止の強調ではなく事実の規定として書く(問題点 4 の方針) |
| 変更範囲 | `post_tool_use.py` の `REMINDER` 定数のみ(ロジック・閾値・発火条件は不変) | 文言の問題であり機構の問題ではない |
| テスト | アサーションを文言の固定部分(「working-notes/ の担当ノート」と手順型構造の「次の手順を実行してください」)の一致へ更新する | 全文一致では文言調整のたびに壊れるため固定部分のみ検査する。手順型構造の部分を含めることで、旧文言への退行をテストで検知できる(レビュー指摘の反映) |
| 追従文書 | state-lifecycle §2 と README 仕組み表のリマインダー説明を新しい趣旨(短い追記と作業復帰を促す)へ更新 | 文書と実装の一致を保つ |
| 先行 spec | rule-firing spec の「注入内容」行に本設計への改訂参照を 1 行注記 | matcher 改訂(2026-08-05)と同じ流儀 |
| 実機知見の記憶統合 | `docs/memory/harness/e2e-verification.md` に今回の実機検証の知見を統合する(発火確認・文言起因の副作用 2 症状・語気過敏と手順型の優位) | rule-firing spec の検証方法 3 で予定していた完了時フロー。「Codex は語気に敏感・手順型が高精度」は今後のハーネス設計全般に効く確定した事実と知識 |

## 新しい注入文言(REMINDER 定数)

```text
working-notes/ の担当ノートが 3 分以上更新されていません。次の手順を実行してください:
1. 現在のタスク専用のノート `working-notes/<topic>.md` があるか確認し、なければ作成する(別タスクのノートを流用しない)
2. そのノートに現在の状態と直近の判断・検証結果を追記する(数行)
3. 中断していた作業を再開する

docs/memory/ への統合はタスク完了時に行う。
```

冒頭の「リマインダー:」ラベルは廃止する(手順の指示文であることが本文から明らかで、
ラベルは情報を足さない)。注入は複数行になるが、JSON 文字列内の改行であり
機構上の問題はない(トークン量も約 120 トークンで上限 2,500 に対して十分小さい)。

## エッジケースの扱い

- **テストとの整合**: 既存テストは「リマインダー」という語の部分一致を検査して
  いるが、新文言にこの語は含まれない(ラベル廃止)。テストのアサーションは
  文言に依存しない検査(additionalContext キーの存在 + 注入文の固定部分
  「working-notes/ の担当ノート」の一致)へ書き換える。
- **リマインダーの再発火**: 手順 1〜2 を実行すればノートの mtime が更新され
  静音化する。手順を無視した場合は従来どおり 3 分ごとに再注入される。

## 検証方法

1. 単体テスト: `python3 tests/test_post_tool_use.py` が全件 green
   (アサーション更新後)。`python3 tests/test_pre_compact.py` も green のまま。
2. 文言確認: hook を手で実行し、注入 JSON に新文言(3 手順 + 統合時期)が
   入ることを確認する。
3. 実機(次回の長時間タスクで観察):
   (a) リマインダー後に「数行追記 → 作業再開」となり、腰を据えたまとめ・
   memory への前倒し統合が起きない、
   (b) ノート未作成の状態では手順 1 によりノートが作成される、
   (c) ノート更新後は静音化する。
