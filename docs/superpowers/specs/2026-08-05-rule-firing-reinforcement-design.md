## 背景と課題

実機運用で次の症状が観測された。

- working-note はセッション初頭の推論でしか作成・更新されず、作業中に推論・検証・
  結果確認が起きてもノートに反映されない。
- `docs/memory/` の検索もタスク開始時にしか行われず、作業中の判断前には発火しない。
- 症状が出たのは「1 ターンが長く、ユーザーへの応答を返さないままツール実行を
  延々と続ける」ケース。

根本原因: 現行ルールは「仮説を立てたら」「判断したら」という**内的事象**を
エージェント自身が検知して行動する自己監視型トリガーになっている。この種の
トリガーはセッション初頭(ルールへの注意が強い間)は発火するが、タスクに
没頭するほど注意が目先のコンテキストへ移り、発火しなくなる。先行設計が拠り所と
する元記事の教訓「プロンプト規範だけに頼ると発動しない → 設定で保証する」に
対して、記録・検索ルールはプロンプト層(AGENTS.md)だけに置かれており、
機械的な裏打ちがなかった。

一次資料で確認済みの事実(2026-08-05 確認):

- Codex hooks には SessionStart / PreCompact / PostCompact のほかに
  **PreToolUse / PostToolUse / UserPromptSubmit / Stop / SessionEnd /
  PermissionRequest / SubagentStart / SubagentStop** が存在する。
- **PreToolUse / PostToolUse / UserPromptSubmit / SubagentStart は
  `additionalContext` によるモデルコンテキストへの注入に対応する**
  (既定上限 2,500 トークン)。PreCompact / PostCompact / PermissionRequest は
  `systemMessage` のみ。
- PostToolUse の matcher は `tool_name`(例: `Bash`, `apply_patch`, MCP ツール名)。
  payload は `turn_id` / `tool_name` / `tool_use_id` を含む。

つまり、先行設計時に検討しなかった「ツール実行ごとに発火し、モデルへ注入できる」
経路が存在する。本設計はこれを使う。

## 決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| 対策の構成 | 案 A(ルールアンカーの行動境界化)+ 案 B(PostToolUse リマインダー hook)の併用 | A で発火点を確実に通過する瞬間へ移し、B で機械的な保険をかける。「ルールは hook で裏打ちする」という先行設計の原則を記録・検索ルールにも適用する |
| 記録アンカー | 「コマンド・テスト・検証を実行して結果を確認した直後」に付け替える。従来の 5 事象(選択・仮説・予想外・事実確認・計画変更)はトリガーではなく「何を書くか」の内容ガイドとして残す | 内的事象の自己検知は発火しない。ツール実行結果の確認はモデルが必ず通過する行動境界であり、かつ推論(予想と結果の照合)が生まれる瞬間と一致する |
| ターン末アンカー | **不採用**(「ユーザーへ応答を返す直前に状態セクションを最新化」は入れない) | 観測された失敗は長い単一ターンで、ターン境界がそもそも訪れないため効かない(YAGNI)。ターン末の取りこぼしは次のツール実行時に hook B が拾い、完了時は既存の統合ルールが拾う。対話型運用で別症状が観測されたら追加する |
| 検索の相乗り | 「ノートに記録するとき、同じトピックのキーワードで `docs/memory/` を grep して関連記憶を確認する」を記録アンカーに統合する。独立トリガー(未知の領域・予想外の結果に直面したら grep)は補助として残す | 検索単独のトリガーも自己監視型で発火しない。確実に発火する記録の習慣に相乗りさせ、トリガーを実質 1 本化する |
| hook イベント | PostToolUse(新規 `.codex/hooks/post_tool_use.py`) | ツール実行ごとに発火し `additionalContext` を注入できる唯一の「長いターンの途中」向け経路。UserPromptSubmit は毎プロンプト消費のわりに長ターン問題に効かず不採用。Stop(ターン末強制)は A+B で不足した場合の将来手段として不採用 |
| 発火条件 | `working-notes/` 配下の最新 mtime が **3 分**を超えて古いとき。ノートが 1 つも存在しない場合も stale 扱い | ユーザーの期待する更新ペースに合わせた(当初案 10 分から短縮)。ノート不存在も拾うことで、タスク開始時のノート作成漏れにも効く |
| クールダウン | 前回注入から **3 分**は沈黙。状態は `.harness/note-reminder-stamp`(空ファイルの mtime、git 管理外)で持つ | 「3 分更新がなければ 3 分に 1 回思い出させる」— リマインド頻度が期待更新ペースと一致する。完全無視の最悪ケースでも約 20 回/時 ≒ 1,000 トークン程度で許容範囲 |
| 定数の置き場 | 閾値・クールダウンは hook 冒頭の定数(`STALE_SECONDS = 180` / `COOLDOWN_SECONDS = 180`) | 運用しながら調整できるようにする |
| 注入内容 | 2 行の定型文(ノート更新と memory grep のルール想起)。ノートの中身は注入しない | hook はどのノートがこのセッションのものか知り得ない(先行設計の判断を踏襲)。誤ったノートの注入は有害だが、内容レスの想起は誤発火してもコストがほぼゼロ |
| フェイルオープン | payload の JSON が不正・想定外でも例外を出さず exit 0。あわせて懸案だった `pre_compact.py` の `json.load` にも同方針の try/except を適用する | hook がツール実行や compaction の妨げになってはならない。同種・同方針の変更なので同スコープで解消する |
| matcher | 実装時に実機で実ツール名を確認して確定する。確認までは一次資料の例示(`Bash` / `apply_patch`)を起点に、実機の tool_name に合わせて広めに登録する | 一次資料の例示と実機の名称が一致する保証がないため、「動くはず」で確定しない |
| 複数セッション時の性質 | mtime・stamp が全セッション共有であることによる偽陰性(他セッションのノート更新で自セッションへのリマインドが抑制される)を許容する | モデル向けナッジは取りこぼし・誤発火のコストがほぼゼロ。かつて mtime 判定の鮮度警告を廃止したのは「ユーザー向け警告として信頼できない」ためであり、ナッジとしての再採用はこれと矛盾しない(用途が違う) |

## AGENTS.md の新ルール文面

「推論の外部化」セクションの記録・検索まわりを次のように改訂する
(冒頭のノート発見・タスク開始時 index 確認・二部構成・再開時・完了時の各箇条書きは不変)。

```markdown
- コマンド・テスト・検証を実行して結果を確認した直後、その時点の推論を
  担当タスクのノートに記録する。タスクの大小を問わない。記録するのは
  行動ログではなく推論: 計画 / 仮説と検証結果(予想と合っていたか)/
  発見 / 判断とその理由(採らなかった案を含む)/ 失敗から得た知識。
- ノートに記録するとき、同じトピックのキーワードで `docs/memory/` を
  grep し、関連する記憶があれば読む。未知の領域・予想外の結果に直面した
  ときも同様に grep する。
```

(現行の「次のいずれかが起きたら、その時点で担当タスクのノートに記録する。
タスクの大小を問わない: (5 事象の列挙)」と「記録するのは行動ログではなく推論: …」
の 2 箇条書きを上記 1 つ目に統合し、「タスク開始時に `docs/memory/index.md` で
関連カテゴリを確認する。作業中に技術判断・予想外の結果・未知の領域に直面したら、
着手前に `docs/memory/` を grep(…)して関連する記憶を読む」の後半を上記 2 つ目に
移す。タスク開始時の index 確認は現行のまま残す。)

## hook の仕様(post_tool_use.py)

- 入力: stdin の JSON payload(`cwd` を使用。他フィールドは使わない)
- 処理:
  1. payload を parse(失敗したら何も出力せず exit 0)
  2. `cwd/working-notes/*.md` の最新 mtime を取得。ファイルがなければ stale 扱い
  3. 最新 mtime が現在時刻から `STALE_SECONDS`(180)以内なら何も出力せず exit 0
  4. `cwd/.harness/note-reminder-stamp` の mtime が `COOLDOWN_SECONDS`(180)以内なら
     何も出力せず exit 0
  5. stamp を touch(`.harness/` がなければ作成)し、`additionalContext` として
     次の 2 行を出力する:
     「リマインダー: working-notes/ の担当ノートが 3 分以上更新されていません。
     直近の判断・検証結果をノートに記録し、関連する docs/memory/ を grep で
     確認してください(AGENTS.md『推論の外部化』)。」
- 出力 JSON の正確なスキーマ(`additionalContext` を包むキー構造)は実装時に
  hooks リファレンスの PostToolUse の例で確認し、実機 E2E で注入されることを
  検証する(「動くはず」禁止)
- 例外時は常に exit 0(ツール実行をブロックしない)

## エッジケースの扱い

- **リマインダーが無視され続ける**: 3 分ごとに再注入され続ける(それ以上の
  エスカレーションはしない。効かない場合は Stop hook 案を将来検討する)。
- **`.harness/` が存在しない**: hook が作成する(pre_compact.py と同じ挙動)。
- **複数セッション並行**: 発火条件・クールダウンとも全セッション共有のため、他
  セッションの更新・注入により自セッションでの発火が抑制されうる(許容。上表)。
- **働いていないセッション(アイドル)**: PostToolUse はツール実行時しか発火
  しないため、アイドル中に鳴り続けることはない。

## 検証方法

1. 単体テスト `python3 tests/test_post_tool_use.py`:
   (a) ノートなし → additionalContext を出力し stamp が作られる、
   (b) 新鮮なノートあり(mtime 現在)→ 出力なし、
   (c) stale なノート(mtime 3 分超過)→ 出力あり、
   (d) stale だが stamp が 3 分以内 → 出力なし、
   (e) stale かつ stamp も 3 分超過 → 出力あり・stamp 更新、
   (f) 不正 JSON / 空 stdin → exit 0・出力なし。
   あわせて `tests/test_pre_compact.py` に不正 stdin → exit 0 を追加。
2. 実機(Codex CLI):
   (a) PostToolUse の実ツール名を確認し matcher を確定する、
   (b) ノートを 3 分放置した状態でツール実行を続けさせ、リマインダー注入と
   「ノート更新・memory grep」の行動変化が起きるか観察する、
   (c) ノート更新後はリマインダーが止まる(静音化)ことを確認する。
3. 実機検証の知見は通常の完了時フローで `docs/memory/harness/e2e-verification.md`
   へ統合する。
